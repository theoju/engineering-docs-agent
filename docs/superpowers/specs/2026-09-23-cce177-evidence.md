# CCE-177 — forensic evidence record: source-collector output truncation

**Captured:** 2026-09-23 · **Repo:** `theoju/engineering-docs-agent` · **Workflow:** `docs-agent-nightly`

## Why this file exists

Each nightly run uploads a `docs-agent-subagent-forensics-<run-id>-1` artifact containing the raw
Claude CLI NDJSON event stream per subagent (`*-source-collector.stream.jsonl`). **GitHub expires
those artifacts 14 days after the run** — the 2026-09-18 one goes around 2026-10-02. This document
is the durable extract: every measurement a root-cause investigation needs, taken while the payloads
were still downloadable. The payloads themselves (~160–250 KB of JSON per run) are deliberately
**not** copied here; only derived numbers and ≤200-char excerpts.

All seven artifacts were present and downloadable at capture time. **Nothing had expired or was
missing.** Analysis was done with Python over the downloaded files.

## 4. Verbosity comparison — same window, 09-17 PASS vs 09-20 FAIL

Both runs processed an identical window. Reassembled payloads confirm it:

- **PR numbers, both runs (identical set of 15):** 265, 264, 263, 241, 239, 238, 237, 232, 231, 228,
  227, 224, 223, 222, 221
- **Jira issues, both runs:** identical set of 30 keys

Same inputs, same shape, same fields (`number, url, title, author, merged_at, merge_sha, body,

sits somewhere between, and nothing in the prompt or the code bounds per-field length.

## 5. Does the payload reassemble?

Two reassembly strategies were tested per failing run: naive concatenation of the assistant text
messages in emission order, and overlap-aware concatenation (drop the longest suffix of A that is a
prefix of B before joining).

| Run | Date | Naive concat parses | Overlap-aware parses | Top-level keys | `len(prs)` | `len(jira_issues)` |
| --- | --- | --- | --- | --- | ---: | ---: |
| `35862057776` | 09-23 | **true** | **true** | `prs`, `jira_issues` | 20 | 38 |
| `35509910089` | 09-20 | **true** | **true** | `prs`, `jira_issues` | 15 | 30 |
| `35343242932` | 09-18 | **false** | **false** | — | — | — |
| `35727627405` | 09-22 | true (single msg) | true | `prs`, `jira_issues` | 19 | 37 |
| `35608299979` | 09-21 | true (single msg) | true | `prs`, `jira_issues` | 15 | 30 |
| `35441305173` | 09-19 | true (single msg) | true | `prs`, `jira_issues` | 15 | 30 |
| `35221636293` | 09-17 | true (single msg) | true | `prs`, `jira_issues` | 15 | 30 |

**Two of three failing payloads are perfectly recoverable by concatenation.** `35862057776` and
`35509910089` produce valid JSON with the expected schema the moment both halves are joined. No
repair, no heuristics — `A + B` parses.

Recovered PR numbers:

- `35862057776`: 281, 279, 278, 277, 276, 274, 265, 264, 263, 241, 239, 238, 237, 232, 231, 228, 227, 224, 223, 222
- `35509910089`: 265, 264, 263, 241, 239, 238, 237, 232, 231, 228, 227, 224, 223, 222, 221

### `35343242932` (09-18) does **not** reassemble — reported honestly

Naive concat fails with `Invalid \escape: line 1 column 177059 (char 177058)`. The 30-char overlap
dedup shifts it to char 177028 but does not fix it. The cause is **not** the split seam — the seam
itself joins cleanly. The corruption is a content-level JSON-escaping fault, and it is confined
entirely to the post-resume continuation half:

| Message | Length | Invalid JSON escapes found by a string-aware scan |
| --- | ---: | ---: |
| 09-18 msg A (pre-truncation) | 161,217 | **0** |
| 09-18 msg B (post-resume) | 31,275 | **14** |
| 09-23 msg A | 159,475 | 0 |
| 09-23 msg B | 90,684 | 0 |
| 09-20 msg A | 164,105 | 0 |
| 09-20 msg B | 8,372 | 0 |

The 14 bad escapes in 09-18's continuation are literal ANSI terminal sequences and unescaped regex
metacharacters, copied into a Jira description that quotes terminal output and Python source. First
offsets within msg B: 15841 `\x1b[`, 15858 `\x1b[`, 16105 `\x1b[`, 24885 `\w.\-`, 24888 `\-/]+`,
24895 `\w.\-`.

Mechanically doubling the two backslashes that block the parser first exposes a second, deeper
fault: at char 177186 a JSON string **closes early** because a quoted Python raw-string regex was
inlined without escaping its own double quotes. The offending region (rendered as Python `repr`, so
`\\n` here is one literal backslash-n inside the JSON string):

```
xes at  tests/templates/test_sdd_fidelity_gate_node.py:23-24  anchor to the start of the line:\n
 _PASS_RE = re.compile(r"^\s*[ℹ#]\s*pass (\d+)\b", re.MULTILINE)
```

The bare `"` characters around `^\s*[ℹ#]\s*pass (\d+)\b` terminate the enclosing JSON string, and
the parser then reports `Expecting ',' delimiter: line 1 column 177188`.

**Conclusion for 09-18:** the payload is corrupt independently of the truncation, and is not
recoverable by concatenation or by mechanical escape repair. Recovering it would require guessing
where string boundaries were intended. The `prs`/`jira_issues` contents of that run are effectively
lost; the window it covered (starting at PR 265 per msg A's opening) is undocumented.

## 6. What the evidence establishes

1. **The established root cause is confirmed in full.** All three failures — and none of the four
   successes — carry exactly one `isSynthetic: true` user turn reading `Output token limit hit.
   Resume directly …`, sitting between two large assistant messages, with the first opening `{"prs":`
   and the second opening mid-string.
2. **The discard is the orchestrator's, not the CLI's.** Every failing run exits `returncode: 0`,
   and `stdout.txt` contains exactly and only the final assistant message. The half carrying
   `{"prs": [` is never captured.
3. **The trigger is per-field verbosity, not window size.** 09-17 (PASS) and 09-20 (FAIL) processed
   an identical 15 PRs / 30 Jira issues; 09-20's payload was 2.9× larger because each `body` and
   `description` was transcribed ~3.4× more verbosely.
4. **Reassembly recovers two of three.** Simple in-order concatenation of the assistant text
   messages yields valid, schema-correct JSON for 09-23 (20 PRs / 38 issues) and 09-20 (15 / 30).
5. **09-18 is unrecoverable, for a second and independent reason:** its continuation half contains
   14 invalid JSON escapes (ANSI `\x1b[`, regex `\w.\-`) plus an unescaped inner `"` from a quoted
   Python regex. Its pre-truncation half is clean, so the escaping quality degraded specifically
   after the resume — worth noting if reassembly is ever considered as a fix.
