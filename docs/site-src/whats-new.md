# What's New

## 2026-06-01T18:14:12.545193+00:00
- PR #91: Migrates the docs-agent-nightly workflow from the deprecated `app-id` input of `actions/create-github-app-token@v3` to `client-id`, and re-classifies `JIRA_EMAIL` from a Repository Secret to a Repository Variable. A CI guard test was added to prevent regression drift across both `.github/workflows/*.yml` and `templates/workflow-*.yml`. The preflight helper gained a `variables_from_workflow` function and a new Variables checklist section in its report output. User-facing setup and operations docs were updated to reflect the new input names and correct GitHub App client-ID formats (both pre-2024 `Iv1.` and newer `Iv23li…` prefixes).
- PR #89: The `markdown_hygiene_structure` lint rule was producing false-positive heading-hierarchy violations whenever a `#`-prefixed line (e.g. a YAML comment) appeared inside a fenced code block. A 13-line surgical fix in `check_path()` now builds `(start, end)` fence ranges from `FENCE_RE` matches and skips any `HEADING_RE` match whose character offset falls within one of those ranges. Two documentation files (plan + spec) were also added capturing the design and implementation detail for CCE-68.
- PR #88: Fixed a two-layer bug where the orchestrator's nightly run committed `.docs-agent-plugin/` as a submodule gitlink (mode 160000) into every host repo's docs-agent PR. The bare `git add .` at `scripts/orchestrator_runner.py:1767` was replaced by an extracted `_stage_docs_run_changes(repo_root)` helper that passes git's exclude pathspec (`':!.docs-agent-plugin'`) so the plugin checkout is never staged. As a belt-and-suspenders measure, the setup skill was updated to instruct new host onboardings to add `.docs-agent-plugin/` to the host's `.gitignore`. A regression test suite was added to lock in the correct staging behavior.
- PR #87: The content-validator subagent previously hardcoded `scripts/lint/lint_runner.py` as the path to the lint runner, which assumed the plugin always lives at the host repo root. When the plugin is vendored under `.docs-agent-plugin/` in CI on external host repos, that path does not exist and every Tier-1 lint rule crashed. The fix adds a `plugin_root` field to the orchestrator's dispatch payload (`scripts/orchestrator_runner.py` +1 line) and updates the `agents/content-validator.md` contract to interpolate `<plugin_root>` when constructing the lint runner invocation. The accompanying spec and plan documents were committed under `docs/superpowers/specs/` and `docs/superpowers/plans/`, and integration tests covering the vendored-path scenario were added.
- PR #84: PR #84 adds `docs.framework: none` as a first-class, valid config value for the engineering-docs-agent plugin. Previously the config schema's `framework` enum was closed to `["mkdocs", "docusaurus"]`, forcing host repos without an SSG (e.g. a Next.js app rendering raw markdown via GitHub) to create a synthetic `mkdocs.yml` and `requirements-docs.txt` purely to satisfy schema validation. The fix updates `templates/config.schema.json` to include `"none"` in the enum, makes `scripts/lint/framework_build.py` emit a clean skip (not a failure) when `framework=none`, and updates `scripts/preflight_host.py` to emit `null` for `publishing.base_url` and `publishing.build_workflow` when no SSG is configured. A new how-to page (`docs/host-onboarding/framework-none.md`) documents the option, what runs vs. skips, and how to upgrade to a full SSG later. Test coverage added across lint, schema, and preflight layers.
- PR #83: Five additive plugin-side changes prepare the `engineering-docs-agent` to onboard `theoju/claude-code-self-assessment` as the first JS/TS host: (1) a vendored-path fix to `templates/workflow-run.yml` so the plugin's CI workflow resolves correctly when installed as a sub-tree; (2) a new `detect_toolchain` function in `scripts/setup_discover.py` that identifies JS/Docusaurus repos alongside the existing Python-MkDocs path; (3) a `tests/fixtures/setup_repos/js_docusaurus/` fixture representing a minimal Docusaurus repo for unit testing; (4) a new read-only `scripts/preflight_host.py` CLI that validates a host repo's prerequisites before install; and (5) an operator runbook `docs/superpowers/specs/2026-05-29-cce57-onboard-runbook.md` covering every partial-mode failure mode identified in CCE-45/49/52/53/55.

## 2026-05-29T20:18:08.098558+00:00
- PR #76: Removed the `paths:` filter from the `pull_request` trigger in `.github/workflows/actionlint.yml`. Previously, actionlint only fired when workflow files changed; now it runs on every PR. The `push: paths:` filter is retained so post-merge runs on `main` still only occur when workflows are actually modified.
- PR #75: Added a `_strip_code_fence` helper to the orchestrator's `dispatch_subagent` function that detects and strips markdown code-fence wrappers (` ```json … ``` `) from subagent output before strict JSON parsing. Previously, the existing `_rescue_json_object` path handled these fences correctly at the content level but appended `prose_contamination_rescued` to `partial_reasons`, causing a 'WARNING — Partial run' banner on every docs-agent PR where any subagent wrapped its JSON in fences (~19% of schema-bearing dispatches on the PR #69 run). The new helper short-circuits cleanly: if the raw output is a bare code fence wrapping valid JSON, strip and parse without marking partial. The rescue path remains intact for genuine prose contamination such as the CCE-15 SessionStart preamble. Two new documentation files (a plan and a spec) were added under `docs/superpowers/` as part of the change.
- PR #74: Applied four code-quality polish fixes to orchestrator_runner.py identified during the CCE-43 Stage 4 /ship review: extracted branch_name(now) into a named local variable (skip_branch), removed a dead KeyError arm from the _remote_already_processed_window except clause, replaced f-string brace-escaped JSON construction with json.dumps(), and replaced a silent third-branch fallthrough with an explicit raise AssertionError. Accompanying tests in test_open_or_append_pr.py were updated to cover the assertion guard.
- PR #73: The pre-flight validation of `CLAUDE_CODE_OAUTH_TOKEN` in both `release.yml` and `docs-agent-nightly.yml` GitHub Actions workflows was hardened from a single non-empty check to four layered checks: (1) empty/missing secret detection, (2) an explicit branch that rejects console API keys matching `sk-ant-api*`, (3) a first-10-chars diagnostic printout for unrecognised token shapes, and (4) a minimum length floor of 32 characters to catch truncated pastes. Expired OAuth tokens remain out of scope.
- PR #72: PR #72 adds a new GitHub Actions workflow (`.github/workflows/actionlint.yml`) that runs `actionlint` as a pre-merge gate on every pull request. The linter checks GitHub Actions context-scoping rules, expression syntax, and other workflow-layer constraints that plain YAML schema validation cannot catch. This closes the gap that allowed a `steps.*` reference at job-env scope to pass local validation but be rejected by GitHub's runtime validator with HTTP 422.
- PR #71: The nightly GitHub Actions workflow's 'Run summary' step replaced a fragile `cat ... 2>/dev/null | sed ... || echo "(no state)"` pipeline with an explicit `if [ -f ... ]` file-existence guard and a `jq -e '.'` one-liner. The old pattern masked `cat`'s non-zero exit code because pipe exit status is swallowed; the new form correctly falls through to the `(no state)` message only when the state file is genuinely absent, and also surfaces invalid JSON via `jq -e`'s non-zero exit.
- PR #70: Bumped two GitHub Actions in the docs-agent-nightly workflow from Node-20-bound majors to Node-24 majors: `actions/create-github-app-token` v1→v3 and `actions/upload-artifact` v4→v6. No workflow logic or behavior changed; only the action version pins were updated.
- PR #68: Added `JIRA_API_TOKEN` and `JIRA_EMAIL` as explicit job-level environment variables in `.github/workflows/docs-agent-nightly.yml`. The docs-agent-nightly workflow now surfaces these repo secrets into the runner environment so the source-collector can authenticate with Jira during each nightly run.
- PR #66: The `GH_TOKEN` GitHub App installation token reference in the nightly docs-agent workflow was moved from job-level `env:` to step-level `env:` on the "Run nightly authoring" step. GitHub's runtime validator rejects `steps.*` context expressions at job scope, so the token reference must live at the step level where it resolves correctly. The token itself (minted via `actions/create-github-app-token`) is unchanged; only its placement in the YAML moved.

## 2026-05-27

### Publish the docs site to GitHub Pages

The docs site can now be published to GitHub Pages through a generic, Node-24-safe GitHub Actions deploy. The setup skill scaffolds a workflow that builds the site, writes `.nojekyll` so the artifact is served verbatim, and publishes it with `upload-pages-artifact` and `deploy-pages` — replacing the legacy Jekyll build that crashed on `{{` and `{%` sequences in source markdown. Non-MkDocs hosts can point it at a custom `build_command` and `site_dir`. See the Operations guide "Publishing to GitHub Pages" for the full flow.
