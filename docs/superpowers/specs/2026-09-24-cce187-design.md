## 0. Context

Nightly run 36080301431 went **blind** on `source_collector_invalid: returned None`. The
source-collector subagent succeeded — returncode 0, empty stderr, 655-byte prompt, 93,015 bytes
of structurally complete output — but its output would not parse. `jira_issues[CCE-75].description`
carried six raw `U+000A` bytes **and** a raw `"`. The first defeats `json.loads`; the second also
defeats `json.loads(strict=False)`. Neither repair layer could help: `_strip_code_fence` only
unwraps fences, and `_rescue_json_object` brace-walks honoring JSON string state, so the stray
quote desynchronizes its depth counter.

The failure is **stochastic**, not a property of the content: run 36007491599 collected the same
window one day earlier and parsed cleanly, having chosen a shorter description for the same issue.

The contract bounds `description` to 1,000 characters and re-verifies that bound three times. It
was obeyed — the failing value ends in the mandated truncation marker. Every guard enforces
*bounded*; none enforces *well-formed*. Full measurement in the evidence doc.

**Direction:** stop asking a language model to hand-serialize prose the orchestrator can fetch
itself. Jira's own REST JSON is well-formed by construction.

## 0.2 What this does and does not close

**It does not fully close CCE-187.** Stated up front because the PR body must say so:

- **Closed structurally:** the Jira half — 57% of the measured corruption surface — because the
  orchestrator parses Jira's own JSON instead of the model's.
- **Closed universally:** the control-character fault, for every field of every agent, via the
  `strict=False` parse tier.
- **Still open:** an unescaped quote inside `prs[].body` / `prs[].title`, ~43% of the surface.
  `_rescue_json_object` desynchronizes on a stray quote and no cheap repair is safe — rebalancing
  quotes inside string values can silently alter content. Filed as **CCE-189**.

## 3. Blocking objections — resolution, one by one

### 3.1 "The defect survives: `prs[].body` is still model-hand-serialised" — **PARTIALLY RESOLVED, residual stated**

The objection is correct and all three designs failed it. Verified: `/Users/theo/Projects/eda-cce181/docs/superpowers/specs/2026-09-24-cce187-evidence.md:122-123` measures `prs` at 39,886 chars / **43%** and `jira_issues` at 52,594 / **57%**. `agents/source-collector.md:292-307` still orders up to 1,000 chars of verbatim PR body.

**Resolution: harden the parse boundary in the same PR, not only the producer.** I ran the committed reproducer:

```
tests/orchestrator/fixtures/cce187_invalid_escaping_source_collector.json  (1628 B, 7 lines)
json.loads(raw)                 -> JSONDecodeError: Invalid control character at char 937
json.loads(raw, strict=False)   -> JSONDecodeError: Expecting ',' delimiter at char 1092
orchestrator_runner._rescue_json_object(raw) -> None
```

Two independent faults: raw U+000A **and** an unescaped `"` (at char ~1092, inside `…treat the path as "explicitly mentioned"…`). So:

- **Add a `strict=False` tier** to the parse fallback at `/Users/theo/Projects/eda-cce181/scripts/orchestrator_runner.py:1438-1451`, and inside `_rescue_json_object`'s terminal `json.loads` at `:1175`. JSON's control-character prohibition is a wire-format rule, not a semantic one — accepting a real newline inside a string value loses nothing and converts a control-char-only corruption from **blind** to **clean**, for *every* field of *every* agent (`prs[].body`, `prs[].title`, and pr-summarizer's four prose fields alike). Reason token `control_chars_tolerated: <agent>`, carried on the existing `out_reasons` channel beside `prose_contamination_rescued` — so it routes through `_record_dispatch_reasons(ok=True)` → `info_only`, and adds **no** `add_partial` call site.
- **Residual, stated plainly:** the *unescaped-quote* half of the class remains open for `prs[].body` and `prs[].title`. `_rescue_json_object`'s brace-walk desynchronises on a stray quote (`orchestrator_runner.py:151-168`) and no cheap repair is safe there — re-balancing quotes inside string values can silently change content. **Measured residual: CCE-187's class is closed for the 57% Jira share and for the control-character fault everywhere; it stays open for an unescaped quote inside `prs[].body`/`title`, which is ~43% of the corruption surface by the evidence table.** File as **CCE-189**, citing CCE-183's thesis (bound/well-form once at dispatch) and the evidence doc's `:149-152`. The honest one-line summary for the PR body: *this closes the Jira half structurally and the control-character half of the PR half; it does not close the class.*

## 6. Failure semantics — 401 / timeout / non-200

`jira_lookup` has exactly two mentions in the orchestrator (`:2635` build, `:2717` read — `grep` confirms), and its single consumer is the advisory `jira_context` input to pr-summarizer at `:2723`. Nothing about the window, `merge_sha`, the CCE-151 cursor, `deferred_pages_by_pr` or `advance_sha` reads it. And `pr_summarizer.schema.json:6` is `additionalProperties: false` with no Jira-shaped property, so Jira content cannot survive downstream as data at all. A Jira failure therefore **holds back enrichment**; it never **consumes** the PRs. Under CCE-144 that is `degraded`, never `blind` — *provided the summary cache does not turn "held back" into "permanently lost,"* which §3.7 fixes.

| Condition | Reason (prefix) | Class | `unresolved_transient` | Run outcome |
|---|---|---|---|---|
| `enabled` false/absent, or zero keys in the capped window | — none — | — | no | today's canonical no-op |
| `JIRA_EMAIL`/`JIRA_API_TOKEN` unset **or empty after strip** | `jira_auth_missing: credentials unset (N keys unresolved)` | `info_only=True` | no | exit 0, `partial` not flipped, watermark advances, auto-merge unaffected |
| 401 / 403 **with** creds present (loop aborts on first — a rejected credential is not per-key) | `jira_auth_missing: credentials rejected (401)` | `info_only=True` | no | as above |
| 404 on some keys (regex false positive, or invisible to the account) | `jira_keys_unresolved: N of M not found (404)` | `info_only=True` | no | as above; those keys omitted, others returned |
| key rejected by regex/prefix, or overflow past `MAX_KEYS_PER_RUN` | `jira_keys_rejected: …` / `jira_keys_capped: …` | `info_only=True` | no | as above |
| **5xx after one retry / read timeout / non-JSON 2xx** | `jira_fetch_degraded: N of M keys unresolved (server_error)` | **`degraded=True`** | **yes** | exit 0, `partial: True`, watermark advances, `blind` never set, affected PRs re-summarized next run |
| deadline reserve exhausted | `jira_fetch_degraded: … (deadline_reserved)` | **`degraded=True`** | **yes** | as above |
| any other exception | `jira_fetch_failed: <ExcType>: <msg[:300]>` | **`degraded=True`** | **yes** | as above |
| agent emitted a non-empty `jira_issues` in production | `source_collector_emitted_deprecated_jira_issues: N discarded` | `info_only=True` | no | exit 0, array discarded |
| residual agent `error: jira_auth_missing` / `jira_partial:` | `source_collector_error: …` | `info_only=True` (was blind) | no | exit 0, watermark advances |

**Why `info_only` for auth and `degraded` for 5xx — the asymmetry, defended explicitly** (this goes in the tripwire audit paragraph, because nothing mechanically checks it):

`degraded=True` flips `partial` (`state_io.py:336-337`), and `orchestrator_runner.py:4705` is `if partial and not advance_cursor_backed: return skip("partial_run")`. So degrading costs a clean non-cursor-backed run its auto-merge.

- **Missing or rejected credentials is a configuration state**, and a permanent one for any host that left `sources.jira.enabled: true` without setting secrets. Degrading there costs that host auto-merge *every night forever* for a condition that will not self-heal. Precedent: the `hard_cap_reasons` loop at `:2491` is `info_only` for exactly this reason.
- **A 5xx / timeout is a transient upstream failure.** The run genuinely judged-and-held-back recoverable work, and with the §3.7 cache suppression the next run really does retry it. That is the textbook `degraded` definition at `state_io.py:310-311`. Under a multi-night Atlassian incident this costs auto-merge — **accepted**, because the alternative is caching empty-Jira summaries for 30 days and calling it green.

Neither reason joins `_MERGE_VETO_REASON_PREFIXES` (`orchestrator_runner.py:4612`, currently `("app_token_unavailable",)`) — a veto would block auto-merge on every night a Jira-less host runs. Nothing mechanically checks that tuple, hence the explicit statement, per the CCE-144 convention.

**The new code never writes `sources["error"]` or `sources["partial"]`**, so it cannot re-inherit the hard-wired blinding; it calls `add_partial` directly.

**Three published docs become true for the first time** (verified today's behaviour is the opposite of all three): `/Users/theo/Projects/eda-cce181/README.md:117-121`, `/Users/theo/Projects/eda-cce181/docs/site-src/setup-guide.md:175`, `/Users/theo/Projects/eda-cce181/docs/site-src/operations/docs-agent-nightly.md:146`.
