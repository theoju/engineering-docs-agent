# Host Onboarding Notes — 2026-05-29

Runbook-level notes from two live onboarding sessions that validated the [setup guide](../setup-guide.md) rewrite (PR #77, CCE-56). Read the setup guide first; this page captures the host-specific deviations and gotchas that extend beyond the generic walkthrough.

Two hosts were onboarded in the same sprint:

- **CCE-57** — a pure JS/TS monorepo (Docusaurus docs, GitHub Actions CI).
- **CCE-58** — a hybrid CI host (CircleCI primary pipeline, GitHub Actions for docs-only workflows).

---

## CCE-57: JS/TS host (Docusaurus)

### Environment

- Framework detected by `setup_discover.py`: `docusaurus`
- Docs source dir: `website/docs/`
- No Python in the repo at all — the agent runs inside the nightly workflow container, so the host doesn't need Python locally.

### Deviations from the generic guide

**Docusaurus sidebar config must be updated manually.** The setup skill writes new pages under `website/docs/`, but Docusaurus won't render them unless they appear in `sidebars.js` (or `sidebars.ts`). Add an `autogenerated` category or explicitly list the agent-editable path:

```js
// sidebars.js
module.exports = {
  mainSidebar: [
    { type: 'autogenerated', dirName: 'generated' },
    // … rest of your sidebar
  ],
};
```

Point `agent_editable_paths` in `.engineering-docs-agent/config.yml` at the same sub-path (`website/docs/generated/**`) so the agent writes only to the autogenerated directory. That keeps human-authored docs and agent-authored docs clearly separated in the sidebar.

**`docs_dir` path in config.** The setup skill prompted for the docs dir and defaulted to `docs/`. On this host you need to correct it to `website/docs/` before committing:

```yaml
# .engineering-docs-agent/config.yml
site:
  docs_dir: website/docs/
  framework: docusaurus
```

**No MkDocs `mkdocs.yml`.** The publish-verification stage looks for `mkdocs.yml` to confirm a successful build. On a Docusaurus host it looks for a Docusaurus build artifact instead. Verify the `publish_verify` block in config points at the right workflow and build output:

```yaml
publish_verify:
  workflow: deploy.yml
  artifact_path: website/build/
```

### Secrets and variables

The secret and variable set is identical to the generic guide. No JS/TS-specific tokens are required.

### Validation result

First automated nightly run completed successfully. Two pages written under `website/docs/generated/`. PR opened as `docs-agent/2026-05-27`. Docusaurus build passed. Sidebar rendered correctly after the `autogenerated` entry was added.

## CCE-58: Hybrid CI host (CircleCI + GitHub Actions)

### Environment

- Primary CI: CircleCI (runs tests, builds, deploys the main app).
- Docs CI: GitHub Actions only (`docs-agent-nightly.yml` and `deploy.yml`).
- Framework: MkDocs (`docs/` source dir, `mkdocs.yml` at repo root).

### Why the hybrid setup is safe

The nightly workflow only needs:

1. A GitHub App installation token (to push the docs-agent branch and open a PR).
2. A `CLAUDE_CODE_OAUTH_TOKEN` to dispatch the Claude CLI.
3. (Optional) Jira and Slack creds.

CircleCI and GitHub Actions workflows are independent pipelines keyed off different events. The docs-agent workflow fires on `schedule` and `workflow_dispatch`. CircleCI fires on push/PR. They don't share a runner or queue — there is no contention.

### Deviations from the generic guide

**Branch protection must allow the GitHub App bypass on the docs-agent branch pattern.** This host had branch protection on `docs-agent/**` enabled as a side-effect of a wildcard rule (`**`). The nightly workflow's push was rejected until the GitHub App was added to the bypass list:

1. Open **Settings → Branches** → find the rule covering `docs-agent/**` or `**`.
2. Under **Allow specified actors to bypass required pull request reviews**, add your GitHub App (search by name, e.g. `theoju-docs-agent-bot`).
3. Save. The next nightly run will push without a protection error.

If the wildcard rule covers too broad a set of branches, scope it more narrowly rather than adding the App as a global bypass.

**CircleCI `config.yml` does not need to change.** The docs-agent branch pattern (`docs-agent/YYYY-MM-DD`) will trigger CircleCI if your config has a branch filter that matches it. That causes spurious CI runs on every docs-agent commit. Filter it out in CircleCI:

```yaml
# .circleci/config.yml — example branch filter
workflows:
  main:
    jobs:
      - build:
          filters:
            branches:
              ignore:
                - /^docs-agent\/.*/
```

Adjust the pattern to match whatever branch prefix you chose in `docs_branch_prefix` (default: `docs-agent`).

**`publish_verify` workflow name.** This host's deploy workflow is named `docs-deploy.yml`, not `deploy.yml`. Update the config:

```yaml
publish_verify:
  workflow: docs-deploy.yml
```

The `publish_verify` stage reads this name to identify which Actions run to watch after the docs PR merges. If it's wrong, the stage times out rather than confirming publication.

### Secrets and variables

Same as the generic guide. SMTP notifications were enabled on this host; add three more secrets:

| Secret          | What it is              |
| --------------- | ----------------------- |
| `SMTP_SERVER`   | e.g. `smtp.gmail.com`   |
| `SMTP_USER`     | Full address            |
| `SMTP_PASSWORD` | App password or token   |

Set `notifications.email.enabled: true` in `.engineering-docs-agent/config.yml` and list recipients under `notifications.email.to`.

### Validation result

First automated nightly run: partial (`jira_auth_missing` — the host doesn't use Jira). That's expected; `jira_issues` is `[]` and the run continues. The docs PR was opened, the deploy workflow triggered, and publish-verification passed. Slack digest sent successfully.

## Common issues across both sessions

**`DOCS_AGENT_APP_CLIENT_ID` in Variables, not Secrets.** Both hosts initially stored the Client ID as a Secret. The workflow reads it as a variable (`vars.DOCS_AGENT_APP_CLIENT_ID`). Move it to the Variables tab; the workflow will stop 404-ing on token minting.

**Stale `origin/main` after merging a docs-agent PR.** The setup guide warns about this in the Plugin conventions section. Run `git fetch` before any follow-up local work after a GitHub-side merge — the local `origin/main` ref doesn't update automatically.

**`actionlint` false positives on `workflow_dispatch` inputs.** CCE-59 (bundled with this PR) changed `actionlint` to `always-run` so it catches these on every commit, not just on tag push. If you see `actionlint` failures after updating the plugin, the failures are real — not pre-existing noise.
