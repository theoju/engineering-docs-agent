# What's New

## 2026-05-29T15:46:56.094919+00:00
- PR #68: Added two job-level `env:` entries to `.github/workflows/docs-agent-nightly.yml` that expose the `JIRA_API_TOKEN` and `JIRA_EMAIL` repository secrets into the docs-agent-nightly runner environment. Because `source-collector` inherits the parent process environment via `dispatch_subagent`, no further plumbing was required beyond this job-env declaration. The fix eliminates the recurring `source_collector_error: jira_auth_missing` partial flag that has appeared on every docs-agent PR since the workflow went live.
- PR #66: Moved the `GH_TOKEN` App-token expression (`steps.app-token.outputs.token`) from job-level env to step-level env on the 'Run nightly authoring' step inside `.github/workflows/docs-agent-nightly.yml`. GitHub's runtime validator rejects `steps.*` references at job-env scope because job-env is resolved before any step executes; the YAML parsed without errors but caused an HTTP 422 when the workflow was triggered via the API. The `CLAUDE_CODE_OAUTH_TOKEN` secret reference remains at job-env scope since `secrets.*` is valid there. Net change: +10/-8 lines, no semantic difference from PR #65.
- PR #65: The `docs-agent-nightly` GitHub Actions workflow was updated to replace the default `GITHUB_TOKEN` with a GitHub App installation token minted from the `docs-agent-bot` app. A new `actions/create-github-app-token@v1` step was added to generate the token using `DOCS_AGENT_APP_ID` and `DOCS_AGENT_APP_PRIVATE_KEY` repo secrets. Both `env.GH_TOKEN` and the `actions/checkout@v5` token input now reference this app token instead of `secrets.GITHUB_TOKEN`. Net diff: +24/-1 lines, workflow YAML only.
- PR #63: Fixed two documentation errors left over from CCE-50: (1) README.md still listed ANTHROPIC_API_KEY in the install steps — replaced with CLAUDE_CODE_OAUTH_TOKEN to match the OAuth token slot the CLI actually reads; (2) docs/setup-guide.md referenced a non-existent workflow filename docs-agent-run.yml — corrected to docs-agent-nightly.yml, which matches the real file in .github/workflows/ and the reference already in README.md.
- PR #62: The orchestrator runner now writes a bulleted digest of `partial_reasons` to `$GITHUB_STEP_SUMMARY` when running inside GitHub Actions. A new `_write_step_summary(state, repo_root)` helper is invoked from a `try/finally` block in `run()`, ensuring the digest flushes even on hard-fail paths (invalid config, corrupted state, or a crash inside `open_or_append_pr`). A shared `_format_partial_digest(partial_reasons)` helper was factored out and reused by both the step-summary writer and the PR body composer, replacing the previous semicolon-joined warning string with a readable bulleted list on both surfaces.
- PR #61: The monolithic `markdown_hygiene` lint rule has been split into two distinct rules: `markdown_hygiene_lang` (severity `warn`) for missing language tags on opening code fences, and `markdown_hygiene_structure` (severity `block`) for unpaired-fence and heading-jump defects that break MkDocs rendering. Three new tests cover each rule and their registration in the lint runner. Existing `markdown_hygiene` tests were renamed to match the new module names.
- PR #60: Corrected the auth environment variable in `docs/setup-guide.md` from `ANTHROPIC_API_KEY` to `CLAUDE_CODE_OAUTH_TOKEN`. The guide now also adds an inline note explaining the OAuth-vs-API-key distinction (OAuth tokens start with `sk-ant-oat…`; console API keys with `sk-ant-api…`), so readers do not need to cross-reference other documents to understand which credential the Claude CLI consumes.
- PR #50: PR #50 hardens the C2 bootstrap stage with three coordinated fail-fast additions: (1) `parse_frontmatter_strict` in `archive_indexes.py` now raises `yaml.YAMLError` versus `ValueError` to distinguish a YAML parse failure from absent frontmatter; (2) a new `description_quality` lint rule — a pure `check_fm` core plus a `check_path` file shim and CLI — is registered as the 8th Tier-1 default rule, rejecting pages whose frontmatter description is too thin or missing; and (3) `dispatch_verified` wraps `dispatch_validated` with a post-write artifact check, while the new `_BootstrapProgress` dataclass atomically records per-page bootstrap state to `.engineering-docs-agent/bootstrap.progress.json` via a temp-file-plus-`os.replace` pattern. 34 new tests (559 → 593) cover all additions, including 7 fail-fast integration tests.

## 2026-05-29T04:34:35.184775+00:00
- PR #58: Adds a `_remote_already_processed_window(repo_root, branch, our_head_sha) -> bool` helper to `scripts/orchestrator_runner.py` that detects same-hour duplicate runs before any subagent is dispatched. The helper fetches `origin/<docs-agent-branch>` and reads its committed `state.json` via `git show`; it returns `True` only when the remote branch's `last_successful_run.head_sha` strictly equals the current run's HEAD SHA. A new call site in `_main()` exits 0 with a skip log line when the helper returns `True`, eliminating the working-tree collision (on `whats-new.md` and `state.json`) that caused the post-CCE-42 smoke-test 2/2 to exit 1. Every failure path — network error, absent branch, missing or corrupted `state.json`, schema drift — returns `False` so the runner proceeds normally. Five unit tests cover all documented failure modes. `skills/engineering-docs-agent/SKILL.md` is updated with a new state-transitions bullet and a renumbered procedure step.

## 2026-05-28T23:15:56.279744+00:00

No Python source changes; the only modified source file is the nightly workflow YAML. Two new internal spec and plan documents were also added under docs/superpowers/.

## 2026-05-27

### Publish the docs site to GitHub Pages

The docs site can now be published to GitHub Pages through a generic, Node-24-safe GitHub Actions deploy. The setup skill scaffolds a workflow that builds the site, writes `.nojekyll` so the artifact is served verbatim, and publishes it with `upload-pages-artifact` and `deploy-pages` — replacing the legacy Jekyll build that crashed on `{{` and `{%` sequences in source markdown. Non-MkDocs hosts can point it at a custom `build_command` and `site_dir`. See the Operations guide "Publishing to GitHub Pages" for the full flow.
