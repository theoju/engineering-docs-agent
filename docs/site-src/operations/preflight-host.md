# Host Pre-flight Check

`scripts/preflight_host.py` is a read-only CLI that runs against any host repo and emits a readiness report before you invoke the setup skill. It shows you exactly what the setup skill would write — without touching any files.

Run it when onboarding a new host, after changing the host's toolchain, or when a workflow update ships and you want to verify the secrets and variables checklist against the current template.

## Usage

```bash
python scripts/preflight_host.py --repo-root /path/to/host
```

Both flags:

| Flag | Required | Default | Description |
| --- | --- | --- | --- |
| `--repo-root PATH` | Yes | — | Absolute or relative path to the host repo root. |
| `--format text\|json` | No | `text` | Output format. Use `json` to pipe the report into other tooling. |

The script always exits `0` on success (even if warnings are present). It exits `1` only when `--repo-root` does not exist.

## Output sections

### Discovery

The discovery block is the raw output of `setup_discover.discover()` (`scripts/setup_discover.py`). Each key maps to one detector:

| Key | Detector | What it surfaces |
| --- | --- | --- |
| `framework` | `detect_framework` | `mkdocs`, `docusaurus`, or `null` |
| `source_dir` | `detect_source_dir` | Docs source path relative to repo root |
| `lens_paths` | `detect_lens_paths` | Top-level subdirectory names as lens keys |
| `ci` | `detect_ci` | `github_actions`, `gitlab_ci`, or `null` |
| `python` | `detect_python` | `{detected, scan_dir, path_root}` |
| `toolchain` | `detect_toolchain` | `{node, bun, deno, package_manager, docusaurus_dep}` |
| `openapi_hint` | `detect_openapi_hint` | Schema filename at repo root, or `null` |
| `jira_hint` | `detect_jira_hint` | `{base_url}` if JIRA markers found, else `null` |
| `pages_publishable` | `detect_pages_publishable` | `true` only for MkDocs + GitHub Actions |

The `toolchain` block is relevant for JS/TS hosts. `node: true` means `package.json` was found. `bun: true` means `bun.lockb` was found. `package_manager` is lockfile-derived (`bun` beats every npm-family lockfile). `docusaurus_dep: true` means any `@docusaurus/*` entry was found across `dependencies`, `devDependencies`, or `peerDependencies`.

### Proposed config

The proposed config shows the `.engineering-docs-agent/config.yml` the setup skill would write, stubbing the notification and lint blocks with safe defaults. The full shape is computed in `scripts/preflight_host.py:proposed_config()`.

Review this block before running the setup skill. If `source_dir` or `lens_paths` looks wrong, investigate why the detector missed the expected path — the detector reads the filesystem directly, so a missing directory or a non-standard config filename is the typical cause.

### Secrets checklist

The secrets checklist is extracted from the shipped `templates/workflow-run.yml` (`scripts/preflight_host.py:secrets_from_workflow()`). It lists every `secrets.X` reference except `GITHUB_TOKEN` (always injected by Actions).

```
[ ] CLAUDE_CODE_OAUTH_TOKEN [required]
[ ] DOCS_AGENT_APP_PRIVATE_KEY [required]
[ ] JIRA_API_TOKEN [optional]
```

Required secrets are `CLAUDE_CODE_OAUTH_TOKEN` and `DOCS_AGENT_APP_PRIVATE_KEY`. The workflow blocks on these two; everything else degrades cleanly (partial run with a `partial_reasons` entry).

### Variables checklist

The variables checklist (`scripts/preflight_host.py:variables_from_workflow()`) lists `vars.X` references from the same workflow template. Variables are set on the **Variables** tab in repo Settings (not the Secrets tab) because they are non-sensitive identifiers, not credentials.

```
[ ] DOCS_AGENT_APP_CLIENT_ID [required]
[ ] JIRA_EMAIL [optional]
```

`DOCS_AGENT_APP_CLIENT_ID` is the GitHub App's OAuth Client ID. Its format depends on when the App was registered: `Iv1.xxxxxxxxxxxxxxxx` for pre-2024 Apps, `Iv23li...` for newer ones. Paste it verbatim.

### Warnings

Warnings are generated by `scripts/preflight_host.py:compute_warnings()`. Each warning has a `code` and a `message`. Three warning codes are currently defined:

| Code | Severity | Meaning |
| --- | --- | --- |
| `framework_none` | info | No `mkdocs.yml` or `docusaurus.config.*` found. The framework-build lint rule and publish-verifier skip; all other capabilities run normally. |
| `pages_not_auto_scaffolded` | info | Docusaurus host without `pages_publishable`. You must set `publishing.build_command` and `publishing.site_dir` manually in config. |
| `node_only_host` | info | Node detected with no Python package. The orchestrator runs from `.docs-agent-plugin/`; this is the expected shape for JS/TS hosts. |

`info` warnings do not block setup. They document gaps you may want to address before the first nightly run.

## Workflow template fix (PR #83)

Before PR #83, `templates/workflow-run.yml` assumed the dogfood repo layout and failed on any non-dogfood host. The fix rewrites the template's checkout logic to check out the plugin repo as a sibling directory rather than assuming it is vendored. This is a generic regression fix — every non-dogfood host benefits, not just JS/TS ones.

If you installed the plugin before this fix landed, re-run the setup skill or copy the updated template from `templates/workflow-run.yml` into `.github/workflows/docs-agent-nightly.yml` in your host repo.

## JSON output

The `--format json` flag emits the full report as a JSON object:

```json
{
  "discovery": { ... },
  "proposed_config": { ... },
  "secrets_checklist": [
    { "name": "CLAUDE_CODE_OAUTH_TOKEN", "required": true },
    { "name": "DOCS_AGENT_APP_PRIVATE_KEY", "required": true },
    { "name": "JIRA_API_TOKEN", "required": false }
  ],
  "variables_checklist": [
    { "name": "DOCS_AGENT_APP_CLIENT_ID", "required": true },
    { "name": "JIRA_EMAIL", "required": false }
  ],
  "warnings": [
    { "code": "node_only_host", "message": "..." }
  ]
}
```

The JSON shape is stable — `secrets_checklist` and `variables_checklist` each return `{name, required}` objects. The `warnings` list returns `{code, message}` objects; `severity` is present when explicitly set and omitted when not (treat absent severity as `block` for backward compatibility).

## When to re-run

Run pre-flight again whenever:

- You change the host's docs framework or source directory.
- A new plugin release ships an updated `templates/workflow-run.yml` (the secrets and variables checklist may change).
- You hit an unexpected partial run — the warnings block often surfaces the cause before you reach the workflow logs.
