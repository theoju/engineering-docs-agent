# CCE-187 evidence — source-collector emits invalid JSON on unescaped prose

**Status:** evidence only. Design lives in the CCE-187 design doc; this file is the raw
measurement, captured 2026-09-24 from GitHub Actions forensics artifacts that expire
2026-10-09 (14-day retention).

Captured because the artifacts are the only copy. The 2026-08-26 repo-fence incident lost a
117-line hook and a 25-test harness that existed only in a session scratchpad; only what had
been echoed into a transcript survived. This is that echo, made durable.

Both ran the **same collection window** (baseline `37f288581f2c`, 2026-09-22T12:31:07Z) one

## The subagent did not fail

From `20260925T011147-source-collector.meta.json`:

- `returncode: 0`
- `stderr`: empty (0 bytes)
- `tool_use.total_calls: 28` — 20 `Bash`, 8 `Read`
- prompt: **655 bytes**

The output is also **structurally complete**, ending in a properly closed `}]}`. So this is
neither a crash, nor the CCE-177 output-split/truncation failure, nor the uncaught
`OSError(E2BIG)` path the CCE-183 payload audit predicted — the 655-byte prompt rules out the
argv ceiling entirely.

## The defect

`jira_issues[CCE-75].description` was emitted with raw newlines **and** raw double quotes
inside the JSON string value. Verbatim, with raw newlines rendered as `⏎`:

```
eckout from being staged as a gitlink (mode 160000)}, added .docs-agent-plugin/ to ADIS/.gitignore to undo the existing gitlink contamination.⏎
⏎
When both are present, git add . -- ':!.docs-agent-plugin' is rejected by git with exit 1 because the negative pathspec causes git to treat the path as "explicitly mentioned" — and then .gitignore rejects it anyway. Root cause is the pathspec/.gitignore interaction, not either change alone.⏎
⏎
ADIS host sid
```

Two independent escaping faults in one value:

1. **Raw `U+000A`** where `\n` was required — rejected by `json.loads` under its default
   `strict=True`.
2. **Raw `"`** around `"explicitly mentioned"` — terminates the string early. This one defeats
   `strict=False` as well, which is why a lenient-parse retry would **not** have rescued this
   run.

## Why both repair layers failed

- `_strip_code_fence` only unwraps a whole-string markdown fence. Not applicable.
- `_rescue_json_object` (`/Users/theo/Projects/eda-cce181/scripts/orchestrator_runner.py:134`) brace-walks the text
  **honoring JSON string state** — tracking open quotes and escape sequences. The stray `"`
  desynchronizes that state machine, so its depth counter is wrong from that point on, and it
  returns `None` at the first `JSONDecodeError` without trying any later candidate.

Correct string-state bookkeeping over corrupt input desynchronizes with certainty rather than
by luck, so the more careful rescue parser is the *more* brittle one against in-string damage.

Net: `dispatch_validated` returns `None` → `add_partial(state, "source_collector_invalid:
returned None", degraded=False)` at `/Users/theo/Projects/eda-cce181/scripts/orchestrator_runner.py:2550` → blind ⇒
exit 1, `_should_advance_watermark` refuses, `_maybe_auto_merge` stops. PR #289 opened, #287
auto-closed, baseline correctly unchanged.

## The length guard worked. It was never the problem.

`/Users/theo/Projects/eda-cce181/agents/source-collector.md:364-400` bounds `description` to 1,000 characters and
re-verifies that bound three separate times in the Step 6 pre-flight. It was **obeyed**: the
failing description ends in the mandated `…[truncated]` marker. The contract never mentions
escaping at any point.

Every guard enforces *bounded*. None enforces *well-formed*. The defect landed in the gap.

The same string also escaped some newlines correctly — it opens
`"description": "Symptom\nADIS docs-agent-nightly silently exited 1..."` — while leaving
others raw. Mixed correctness **within a single value** is the signature of hand-serialization
drift, and it is why no pre-flight instruction the agent checks against itself can be trusted
to close this.

## Reproducer

`/Users/theo/Projects/eda-cce181/tests/orchestrator/fixtures/cce187_invalid_escaping_source_collector.json` is the
CCE-75 record lifted byte-for-byte from the failing payload and wrapped in a minimal envelope
(1634 bytes). It reproduces both faults:

```python
import json
s = open("tests/orchestrator/fixtures/cce187_invalid_escaping_source_collector.json").read()
json.loads(s)                 # JSONDecodeError: Invalid control character at char 937
json.loads(s, strict=False)   # JSONDecodeError: Expecting ',' delimiter at char 1092
```

No pre-existing fixture covered this class: `tests/orchestrator/fakes_bad_json/fake_source_collector.json`
parses cleanly (its scenario is malformed output from a *different* agent in the set).
